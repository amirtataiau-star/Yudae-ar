# Yudae Commons | Detail–Possibility–Consequence Register v0.3

**Purpose:** Prevent environmental detail from becoming decorative, falsely certain, or an unaccountable optimisation game. This is a *fictional* branching pilot, not a validated model of emergency services or clinical practice.

## Design integrity rules

1. **Observation ≠ truth.** Every inspectable detail distinguishes a visible trace from what it cannot establish. Voices have situated knowledge, not omniscience.
2. **Discovery ≠ action.** Inspecting an object reveals evidence. A participant can optionally commission one focused inquiry, consuming a volunteer/steward's limited attention. The inquiry never powers anything or guarantees a solution.
3. **Decision ≠ control.** Allocation remains a recommendation to Yudae's site team; the site team authorises the actual battery move.
4. **Consequences remain relational.** Power changes material conditions; communication changes whose accounts may circulate and whose needs remain outside reach.
5. **No moral score.** The agential-wellbeing lens remains optional and qualitative, not an optimal-path meter.
6. **Revisability and accessibility.** Participants can make choices without inspection, revisit consequences and revise recommendations. The evidence interface works under the map fallback, not just the 3D renderer.

## Implementation notes

- Six button-accessible evidence records exist in both visual modes. Numbered 3D hotspots assist discovery **in the embedded web 3D viewer**; Android's separate AR viewer may not display these interactive HTML hotspots. The matching list remains available on return.
- State persists as `inspected`, `objectFocus`, `followUp` in local browser storage, alongside the earlier decision history.
- Two decisions form **six allocation/communication combinations**, with optional focused inquiries branching the authored consequence text. There is no hidden correct choice.
- Observation records remain in the history when a recommendation is revised. Superseded decisions are marked separately.
- 3D files remain the verified v0.2 scenario states. v0.3 improves the interpretive/action layer and spatial hotspots; it does not pretend that each new evidentiary object has acquired a new fully modelled mesh.

## Tests performed

- All 3 allocation options × 2 communication routes; logger inquiry follows through to ending.
- Map fallback, charger inquiry, revision of first choice, no horizontal overflow at 360/390/768 px; no JavaScript page errors in these simulated browser paths.
- **Not verified**: actual device AR hotspot rendering, outdoor lighting/surface placement, screen-reader usability with a person, empirical changes in participants' interpretation or wellbeing.

## Next audit questions for human pilot

- What did participants notice before reading text? What did they assume about the environment without sufficient grounds?
- Which inquiries changed their understanding, and which merely increased screen time?
- Do objects make previously unseen obligations and alternative possibilities salient without turning into clues for a single right answer?
- What burdens does selecting one inquiry place on an already stretched person? Is that cost visible?
- Are object hotspots useful in 3D, or is the accessible list enough? Does moving in physical space add anything that the map cannot?
